# 议题:把 LLMComponent 的"自定义大模型客户端"补成一个真正能用的扩展点

> 目标仓:`openJiuwen/agent-core` ｜ 依据版本:openjiuwen **0.1.16**
> 类型:能力完善(以新增与文档为主,**不改变任何现有默认行为**)

---

## 一、主张

框架**已经**为"自定义大模型客户端"留了一条路——不是没有，是**有一半**。

但这条路今天基本没法用：没有任何文档说它存在，没有说明你要实现什么，
框架还会在你不知情的情况下改写你交进去的对象；出错时也看不到真正的原因。

**本议题不是请求增加一个新功能，而是把这条已经存在的路补完整、说清楚。**
主要涉及 `LLMComponent` 及其背后的 `Model` 与客户端工厂。

---

## 二、现状

### 2.0 先说清楚在讨论什么

在 openJiuwen 里搭一条工作流时，"问一次大模型"这个环节由 **`LLMComponent`** 承担。
它负责拼提示词、发起调用、把结果解析成结构化输出。而**真正把请求发到大模型服务上去**
的那段代码，叫**客户端**（client）——负责用什么协议发、怎么带鉴权、连接怎么管、
超时怎么算。

框架内置了 9 种客户端（OpenAI、Anthropic、DeepSeek、DashScope、SiliconFlow 等）。
本议题讨论的是：**当你需要的后端不在这 9 种里时，怎么接进来。**

### 2.1 好消息:这条路是通的

读源码可以确认，自定义客户端**确实能接**，一共三步：

```python
# 第一步:注册一个工厂
get_client_registry().register_client("my-backend", client_type="llm")(my_factory)

# 第二步:配置里把 provider 写成这个名字（它接受任意字符串，不限于内置枚举）
ModelClientConfig(client_provider="my-backend", client_id="...")
```

第三步是框架自己做的：`create_model_client()` 先在 9 个内置里找，找不到就**回落到注册表**。

**所以扩展能力是存在的。问题全部出在"这条路好不好走"上。**

### 2.2 问题一:没有任何地方告诉你这条路存在

这个注册表是一个**通用**的客户端注册表，它的说明和示例讲的是 Redis、MySQL
（`client_type="common"`），完全看不出来还能用来接大模型。
LLM 只是它众多使用者中的一个，而且是以"找不到内置的就试试这里"的兜底方式用的。

一个新用户按正常路径去看文档、看 `LLMComponent` 的配置项，**是发现不了这条路的**。

**顺带一提**，注册失败时的报错也会误导：

```
Unsupported client_provider: 'x', Supported types: [...]
```

这个"支持列表"里**只有注册表中的自定义客户端，不包含 9 个内置的**——
因为内置的在更早一步就返回了，根本没走到这里。第一次用的人看到的是一份不完整的清单。

### 2.3 问题二:你要实现成什么样,没有任何说明

假设你发现了这条路，接下来你会立刻卡住，因为下面这些**没有一处写在文档里**，
只能靠读框架源码倒推：

- 你的工厂函数会被用 `model_config=..., model_client_config=...` 两个关键字参数调用；
- 你返回的对象会被 `Model` 包起来，而 `Model` 调用它的方式是固定的：

  ```python
  await self._client.invoke(
      messages=..., stop=..., model=..., tools=...,
      temperature=..., top_p=..., max_tokens=...,
      output_parser=..., timeout=..., **kwargs
  )
  ```
  并且期待返回一个 `AssistantMessage`。

- 工厂的返回类型标注写的是 `BaseModelClient`，但实际并不强制。
  那到底要不要继承这个基类？基类里还有生成图像、语音、视频的方法——
  内置实现里这几个是空的、直接返回 `None`。你要不要实现？**说明里没有答案。**

也就是说：**能力在，契约不在。** 想接一个客户端，你得先把框架源码读一遍。

### 2.4 问题三:框架会改写你交进去的对象

`Model` 在构造时，为了挂上回调事件，做了这样一件事：

```python
self._client.invoke = fn     # 把你对象上的方法直接替换掉
self._client.stream = fn
```

这带来三个后果：

1. 你的对象**必须允许被随意改属性**。如果你出于安全或性能用了 `__slots__`、
   或者用了不可变的数据类，**直接报错**，而且错得莫名其妙。
2. 你以为在跑自己写的方法，实际外面已经套了三层包装。出问题时调用栈会很难读。
3. 如果你把 `invoke` 写成了属性（property）或别的形式，行为无法预期。

框架想在调用前后插入事件，这个需求完全合理。但**包装应该做在框架自己这一侧**
（自己持有一个包装后的可调用对象），而不是去修改别人交进来的对象。

### 2.5 问题四:不能直接把一个现成的客户端交给它

`LLMComponent` 拿到的是**配置**，不是对象。它内部自己造：

```python
def _create_llm_instance(self):
    if self._config.model_id is None:
        ...
        return Model(self._config.model_client_config, self._config.model_config)
    else:
        return await Runner.resource_mgr.get_model(id=self._config.model_id)
```

只有这两条路。于是你没法把一个**已经建好的**客户端交给它——
比如一个已经建好连接池、需要被多个组件共享的实例。

**测试时这一点尤其难受。** 想给一条工作流写单元测试，最自然的做法是塞一个
假客户端，让它返回固定结果，这样就能又快又稳地验证流程逻辑。
但现在你得先去全局注册一个 provider 名字、编一套配置，绕一大圈才能做到。
结果就是**大家干脆不写这类测试，或者每次测试都真的去调模型**——慢、花钱、还不稳定。

### 2.6 问题五:出错时看不到真正的原因

这是我们实际排查时最痛的一点。`LLMComponent` 调用失败时是这样处理的：

```python
except Exception as e:
    if UserConfig.is_sensitive():                     # 默认就是 True
        raise build_error(..., error_msg="invoke llm failed", cause=e) from e
    else:
        raise build_error(..., error_msg=str(e),      cause=e) from e
```

默认情况下，**真实的失败原因被替换成了固定的一句 `invoke llm failed`**，
原始异常只挂在 `cause` 上。而错误对象无论转成字符串还是转成字典，
**都不包含 `cause`**。于是上层日志里能看到的就只有那一句话。

是超时？是连接被重置？还是服务端返回了 401？**看不出来。**
要看到真实原因，得设一个环境变量 `IS_SENSITIVE=false` 再跑一遍。

脱敏的初衷是对的——不该把提示词和用户数据写进日志。
但**"失败原因和异常类型"不是用户数据**，把它一起脱掉，代价是排查成本成倍上升。

> 我们遇到过内置客户端在持续高负载下大量调用失败的情况，同一个后端换成自己写的
> 客户端就完全正常。那个缺陷本身当然会被修复；但当时真正让我们难受的是两件事：
> **一是排查时看不到失败原因，二是即使定位到了，也没有一条像样的路把自己的客户端接进去。**
> 本议题针对的是后面这两件事——它们与那个具体缺陷是否修复无关。

## 三、方案

六条，按重要性排列。**每一条都是新增或改文案，不动任何现有默认行为。**

### 3.1 把契约写出来,并标成公开接口

不需要重新设计——**把框架现在实际在用的调用方式写下来即可**：

```python
class LLMClient(Protocol):
    """自定义大模型客户端需要满足的契约。"""

    async def invoke(self, messages, *, tools=None, temperature=None, top_p=None,
                     max_tokens=None, stop=None, model=None,
                     output_parser=None, timeout=None, **kwargs) -> AssistantMessage:
        """发一次请求，等完整结果。"""

    def stream(self, messages, *, ...) -> AsyncIterator[...]:
        """发一次请求，流式返回。"""
```

同时在文档里说清三件事：**工厂会被怎么调用**、**要返回什么**、
**要不要继承 `BaseModelClient`**（建议答案是"不必"——用 Protocol 表达契约，
实现方不需要继承框架的任何类，甚至不需要 import 框架，只要方法对得上）。

对内置客户端来说这是**零改动**，它们本来就满足。

### 3.2 允许直接传一个现成的实例

给 `LLMComponent` 和 `Model` 各加一个可选参数：

```python
LLMComponent(config, client=my_client)     # 传了就用它，不传就走原路径
```

这一条解决 2.5 的全部问题，**尤其是让"用假客户端写流程测试"变成一行代码**。

### 3.3 不要改写别人交进来的对象

回调包装改为框架自己持有：

```python
# 现在:改别人的对象
self._client.invoke = wrapped

# 建议:自己拿着包装后的版本
self._invoke = wrapped
```

功能完全一样，但不再要求交进来的对象"必须可以被随意改属性"。

### 3.4 报错要带上真实原因

- 错误对象转成字符串和字典时，**默认带上原始异常的类型和简要信息**；
- 脱敏只脱**内容**（提示词、返回文本），不脱**失败原因**。

这样默认情况下就能看出是超时还是连接问题，不必设环境变量重跑一遍。

### 3.5 报错里的"支持列表"要完整

把 9 个内置 provider 也列进去，否则那份清单会误导人。

### 3.6 顺手修一处文档错误

`Model` 的说明里写的是 `Model(model_config, client_config)`，
而真实签名是 `Model(model_client_config, model_config)`——**顺序正好相反**。
照文档写就会传反，且不一定立刻报错。

## 四、兼容性

- 新增的都是**可选参数**，不传时行为与现在完全一致；
- 契约是把现有行为写下来，内置客户端无需改动；
- 3.3 是内部实现调整，对外表现不变；
- 3.4/3.5/3.6 只影响错误信息与文档。

**现有用户不需要修改任何代码。**

---

## 五、分两步做

| 步骤 | 内容 |
|---|---|
| **一** | 3.1 契约与文档 + 3.2 允许传实例 + 3.5/3.6 文案修正——**纯新增，风险最低** |
| **二** | 3.3 包装方式调整 + 3.4 错误信息带原因——涉及内部改动，需配测试 |

**怎么算做成了**，建议以这四条为准：

1. 不传 `client` 时，现有测试全部通过、行为不变；
2. 照着文档，能在**不读框架源码**的前提下接入一个自定义客户端；
3. 用一个假客户端跑通一条带分支的工作流测试，**全程不连任何真实模型**；
4. 故意让客户端抛一个超时异常，上层日志里**能直接看出是超时**。

第 2 条是这个议题的核心目标：**判断标准不是"能不能接"，而是"用不用读源码才能接"。**

---

## 六、我们能提供什么

- 一份按此契约实现的自定义客户端，作为文档示例；
- 上述四条验收的测试用例；
- 内置实现与自定义实现在真实负载下的对照数据。

---

## 七、明确不做

- **不替换、不修改**任何内置客户端；
- **不重新设计**调用签名——只是把现有的写下来并标成公开接口；
- **不引入新依赖**；
- 图像/语音/视频生成不在本议题范围内，建议另立各自的契约。
