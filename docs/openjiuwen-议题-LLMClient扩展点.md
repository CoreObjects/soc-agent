# 议题:为 openJiuwen 增加一个面向高并发生产场景的 LLM 客户端

> 目标仓:`openJiuwen/agent-core` ｜ 依据版本:openjiuwen **0.1.16**
> 类型:新增一个客户端实现(**不改动框架现有任何默认行为**)

---

## 一、主张

openJiuwen 的工作流编排能力是好用的——组件、条件分叉、结构化输出，
我们在真实项目中一直在用，也会继续用。

问题出在**更下面的一层**：真正把请求发到大模型服务上去的那段代码，
框架里叫**客户端**（client）。它负责用什么协议发、连接怎么管、超时怎么算、
失败了怎么重试。**这一层在"持续高并发、长时间不停跑"的生产场景下，实测扛不住。**

**我们主张：为框架增加一个面向高并发生产场景的 LLM 客户端。**
我们已经有一个在同一个后端、同等负载下稳定运行的实现，愿意按框架规范整理后贡献出来，
接受社区评审。

这不是要替换或否定现有的客户端——现有实现在低频、交互式的场景下工作得很好。
我们要补的是**另一类场景**：后台不间断跑、调用量以万计、必须长时间稳定。

---

## 二、现状:内置客户端在生产负载下的实测问题

下面每一条都来自真实运行，不是推测。

### 2.1 决定性证据:持续高负载下,约一半调用失败

我们做过一组**只有一个变量**的对照实验：

| | 用哪个客户端 | 后端 | 调用量 | 结果 |
|---|---|---|---|---|
| A | **框架内置的客户端** | 同一个服务、同一个模型 | 约 6.5 万次 | **约 50% 失败** |
| B | 自己写的客户端 | **完全相同** | 同期 | **0 失败** |

两组唯一的差别就是客户端。后端、模型、网络、机器全都一样。

还有一个细节值得注意：把日志按时间劈成前后两半，失败次数几乎相等
（35.07 万 vs 35.22 万）。也就是说**从第一次调用起失败率就是 50%，不是跑着跑着才变差的**。
这排除了"连接泄漏、越跑越糟"这一类解释，指向一个从一开始就存在的结构性问题。

### 2.2 最可能的原因:连接不复用,每次调用都重新建一遍

读源码可以看到，内置客户端**每一次调用**都会新建一个 HTTP 连接对象，
调用结束立刻销毁：

```python
# 每次 invoke / stream 都执行
async_client = httpx.AsyncClient(...)      # 新建
...
finally:
    await async_client.close()             # 用完就关
```

而且新建时**没有设置任何连接数上限和保活参数**。

这意味着每一次调用，都要重新完成一遍完整的 TCP 建连和 TLS 握手，用完就丢。
低频使用感觉不出来；一旦持续高频调用，就会不断产生和销毁大量连接，
系统的临时端口和文件句柄会剧烈波动，握手失败的概率显著上升。

**一个值得一提的地方是：框架其实已经写好了连接池**
（`common/clients/connector_pool.py`，连接数上限、保活时间、生存期都齐全），
**只是没有接到 LLM 这条路上**。也就是说，这更像是一处没接上的线，而不是缺失的能力。

### 2.3 失败时看不到真正的原因

调用失败时，框架的处理是这样的：

```python
except Exception as e:
    if UserConfig.is_sensitive():                     # 默认就是 True
        raise build_error(..., error_msg="invoke llm failed", cause=e) from e
```

真实的失败原因被换成了固定的一句 `invoke llm failed`，原始异常挂在 `cause` 上。
而错误对象**无论转成字符串还是字典，都不包含 `cause`**——
于是日志里能看到的就只有那一句话。

是超时？是连接被重置？还是服务端返回了 401？**看不出来。**
想看到真实原因，得设一个环境变量 `IS_SENSITIVE=false` 再整个跑一遍。

这一条本身不会导致失败，但它让上面 2.1 那个问题**极难定位**——
我们是靠通读框架源码才找到方向的。

### 2.4 没有退避重试,也没有熔断

组件调用大模型时不做任何重试控制，唯一的重试是交给底层 SDK 的固定次数重试。
后果是：后端一旦抖动，请求会**不带间隔地反复打过去**，把本来就紧张的后端压得更死；
也没有熔断机制在连续失败时先停一停。

### 2.5 默认超时配置不适合大模型

默认是"单次 60 秒超时 + 重试 3 次"。大模型一次推理经常超过 60 秒，
于是实际表现是：**一次调用要等大约 4 分钟才最终报失败**（60 秒 × 4 次尝试）。

而且这个超时是**一个总时长**，不区分"连上服务器要多久"和"等结果要多久"——
这两件事的合理取值差着一个数量级。

### 2.6 思维链没有开关,默认不关会导致结果解析失败

现在很多模型（如 qwen3）默认会先输出一段"思考过程"再给答案。
这段内容混在返回里，会让期待 JSON 的解析直接失败，报一个 `Json parse error`。

框架没有提供关掉它的正式选项，只能靠一个"额外参数"字段手工往下透传特定的键值。
不知道这个技巧的人，第一次接这类模型就会踩到，而且报错信息完全指不到病根。

### 2.7 并发受限

框架的执行器是**进程级的单个实例**，并且绑定在单一事件循环上。
我们实测**两个并发就会跑不到出口、结果为空并挂死**，单线程则完全正常。

> 这一条严格说不属于客户端，而是执行器的问题，已另行反馈。
> 这里提到它，是因为它和"能不能并发使用"直接相关：
> 即使客户端本身支持并发，上层这个限制仍会把吞吐卡住。
> 我们贡献的客户端会保证自身**不引入新的并发限制**（见 3.6）。

## 三、方案:我们要贡献的客户端做到什么

七条，每一条都对应上面的一个问题。

### 3.1 连接复用

全局维护一个带连接池的 HTTP 客户端，设置合理的连接数上限与保活时间，
**不再每次调用新建和销毁**。这是 2.1 / 2.2 的直接解法。

### 3.2 超时分级

把"连接超时"和"读取结果超时"分开配置。前者应该很短（连不上就快点失败），
后者要给足（大模型本来就慢）。不再用一个总时长一刀切。

### 3.3 退避重试 + 熔断

重试之间加递增的等待间隔，避免在后端抖动时反复冲击；
连续失败达到阈值时先短暂停止，给后端恢复的时间。
同时区分"值得重试"（超时、连接重置）和"重试也没用"（参数错误、鉴权失败），
后者立即失败，不浪费时间。

### 3.4 思维链一等开关

把"要不要输出思考过程"做成一个**正式的配置项**，由客户端负责翻译成各家后端
自己的写法，而不是让使用者去猜该往哪个字段里塞什么。

### 3.5 失败原因完整透传

异常里保留原始的错误类型和信息，让上层日志**默认**就能看出是超时还是连接问题，
不需要改环境变量重跑。脱敏只脱提示词和返回内容，不脱失败原因。

### 3.6 不绑定事件循环,支持并发调用

同一个客户端实例可以被多个并发请求同时使用；
不在创建对象时就绑定事件循环，换线程使用不会出问题。

### 3.7 与现有配置体系兼容

沿用框架现有的配置对象和调用签名，**对使用者来说只是换一个 provider 名字**，
工作流本身一行都不用改。

## 四、怎么接进来

分两个阶段，风险从低到高。

### 阶段一:以自定义 provider 的方式接入,不改框架任何代码

框架的客户端创建逻辑是：先在内置的 9 种里找，**找不到就回落到一个注册表**。
而配置里的 provider 字段接受任意字符串。

这意味着我们的客户端可以**先以注册的方式接进去**，
不需要修改框架源码，也不影响任何现有用户：

```python
get_client_registry().register_client("high-concurrency", client_type="llm")(factory)
```

```python
ModelClientConfig(client_provider="high-concurrency", ...)
```

先在真实负载下跑一段时间，把数据拿出来。

### 阶段二:验证通过后,考虑合入内置

如果对照数据成立，再讨论两种走法（由社区决定）：

- **走法甲**：作为第 10 个内置 provider 加入，供有高并发需求的用户显式选用；
- **走法乙**：把其中的连接复用、超时分级等部分，直接合并进现有内置客户端。

走法乙收益更大（所有用户都受益），但改动面也更大，需要更充分的回归验证。
我们建议先甲后乙。

---

## 五、怎么验证

我们会提供一份对照压测数据，两边条件完全一致：

| 项目 | 说明 |
|---|---|
| 对照组 | 现有内置客户端 |
| 实验组 | 新客户端 |
| 控制变量 | **同一个后端服务、同一个模型、同一台机器、同样的请求内容** |
| 调用量 | 各不少于 5 万次 |
| 记录指标 | 成功率、平均耗时、95 分位耗时、系统连接数变化曲线 |

判断标准很简单：**成功率必须显著提升，且耗时不能变差。**
如果做不到，这个议题就不该通过。

另外还要满足：

1. 不选用新客户端时，现有测试全部通过、行为完全不变；
2. 新客户端在并发 32 的情况下连续跑满一小时不出错。

---

## 六、收益

- **对使用方**：高并发场景下调用不再大面积失败，故障也能定位得动；
- **对框架**：补上一类目前覆盖不到的使用场景（后台长时间高频调用），
  并把已经写好但没接上的连接池真正用起来；
- **对社区**：贡献一份带完整对照数据的实现和测试用例。

---

## 七、明确不做

- **不改动**现有的 9 个内置客户端（阶段一完全不碰）；
- **不改变**任何默认行为，不选用就等于这个议题不存在；
- **不重新设计**调用接口，沿用现有签名；
- **不处理**执行器的并发限制（2.7）——那是另一个问题，已另行反馈；
- **不引入**新的第三方依赖。
