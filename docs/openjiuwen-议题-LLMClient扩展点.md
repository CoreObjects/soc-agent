# 议题:让"调用大模型的那段代码"成为可替换的扩展点

> 目标仓:`openJiuwen/agent-core`
> 类型:能力增强(新增扩展点,**不改变任何现有默认行为**)

---

## 一、主张

一个智能体框架做的事，可以分成两半：

- **上半**：决定什么时候该问大模型、问什么、拿到回答之后怎么走下一步。这是编排、会话、
  流程控制——**框架的核心价值所在**。
- **下半**：真正把这次请求发到大模型服务上去。用什么协议、怎么鉴权、连接怎么管理、
  超时和重试怎么处理。

今天这两半是焊死在一起的：**下半只有框架自带的两种实现，想换一种就得改框架源码。**

本议题主张把下半独立出来，定义成一个**公开的小接口**。框架继续管好上半，
下半允许使用者自带实现。框架自带的实现照旧保留，成为这个接口的两个参考实现。

---

## 二、现状

### 2.1 今天是怎样的

框架内置了两个大模型客户端（OpenAI 与 Anthropic），代码在
`core/foundation/llm/model_clients/` 下。要接第三种后端——比如别的推理服务、
公司内部的模型网关——**没有对外的接入方式，只能改框架源码或绕过框架**。

框架内部确实有一个抽象基类，但它并不是为"给外部人实现"设计的：

- 它要求实现的方法**远多于**框架实际会调用的（还包含图像、语音、视频的生成方法，
  而内置实现里这几个是空的、直接返回 `None`）；实现者无从判断哪些必须写、哪些可以不写。
- 没有任何文档说明它是一个可扩展点，也没有说明实现时必须遵守哪些约束。

### 2.2 这会带来什么问题

**① 后端换不了。** 大模型服务的接口并不统一。OpenAI 风格只是其中一种，
还有各家自研的推理服务和企业内部网关。框架只支持两种，等于把可接入范围写死了。

**② 企业的特殊要求塞不进来。** 内部鉴权系统、双向证书、经过代理访问、
多部门配额限制、调用留痕审计——这些每家都不一样，**不该由框架来实现**，
但必须**有地方让使用者自己实现**。现在没有这个地方。

**③ 测试困难。** 想给一条工作流写单元测试，绕不开真实的大模型服务：慢、要花钱、
结果还不稳定。如果客户端可以替换，塞一个"假客户端"就能把流程逻辑测得又快又确定。

**④ 出问题时没有退路。** 内置客户端一旦有缺陷，使用者只能等框架发新版本。
我们实际遇到过这种情况：内置客户端在持续高负载下大量调用失败，
而同一个后端换成自己写的客户端就完全正常。那个缺陷本身当然会被修复，
但当时真正卡住我们的不是缺陷，而是**没有任何合法的替换方式**。

> 补充一点：把客户端独立出来，**框架自己也受益**。
> 一旦使用者面对的是"接口"而不是"某个具体实现"，框架就可以放手改造内置实现
> （优化连接管理、加重试熔断），不必担心破坏别人的代码。

## 三、方案

### 3.1 定义一个小接口

关键是**小**。只包含框架真正会调用的东西：

```python
class LLMClient(Protocol):
    """把一次对话请求送到某个大模型服务，并取回结果。"""

    async def invoke(self, request: LLMRequest) -> LLMResponse:
        """发一次请求，等完整结果返回。"""

    def stream(self, request: LLMRequest) -> AsyncIterator[LLMChunk]:
        """发一次请求，结果分块流式返回。"""

    @property
    def capabilities(self) -> Capabilities:
        """自报支持哪些能力（见 3.3）。"""

    async def aclose(self) -> None:
        """释放连接等资源。"""
```

`LLMRequest` 是一个**与厂商无关**的请求描述：消息列表、模型名、温度、
最大长度、可调用的工具、期望的返回格式、超时设置等。各家后端的差异，
由各自的实现去翻译。此外保留一个 `extra` 字段放厂商私有参数——
**没有这个口子，每多一个厂商的特殊参数，都会变成一个框架 PR**。

用 `Protocol`（结构化类型）而不是抽象基类的好处是：**实现者不需要继承框架的任何类，
甚至不需要 import 框架**，只要方法签名对得上即可。这让双方的耦合降到最低。

### 3.2 三种用法

```python
# ① 直接传一个实例 —— 最常见
model = init_model(..., client=MyClient(...))

# ② 给某个组件单独指定 —— 一条流程里不同环节可以用不同后端
LLMComponent(..., client=MyClient(...))

# ③ 先注册一个名字，再在配置文件里引用
register_llm_client("my-backend", lambda cfg: MyClient(**cfg))
```

```yaml
llm:
  client: my-backend
  client_config: { endpoint: "..." }
```

第 ③ 种不是可有可无的。框架正在往"用配置文件描述工作流"的方向发展，
如果扩展点只能在写代码时用，它在框架主推的使用方式上就是失效的。

### 3.3 能力自报 + 提前检查

不同后端支持的功能不一样：有的能调用工具，有的不能；有的模型会输出思考过程，
需要关掉才能拿到干净的结果。所以客户端要**自报支持什么**：

```python
class Capabilities:
    stream: bool            # 支持流式
    tool_call: bool         # 支持调用工具
    json_schema: bool       # 支持按指定格式返回
    reasoning_toggle: bool  # 能否关闭思考过程输出
```

框架据此在**搭建流程的时候**就检查，而不是等到运行时：
如果某个环节要求结构化输出，而客户端两种方式都不支持，**当场报错并说清楚原因**。

> 这能消除一类很难查的故障：某些模型默认会输出一段思考过程，
> 混在结果里导致解析失败。现在它表现为运行时的一个笼统报错，
> 排查起来要花很久；提前检查后，它变成搭建时的一句人话提示。

### 3.4 几条必须写进文档的规则

接口只写方法签名是不够的，下面几条约束必须明确，否则每个新实现都会重犯同样的错：

1. **同一个客户端实例要能被并发使用**，不能假设一次只有一个请求。
2. **不要在创建对象时就绑定事件循环**，否则换个线程使用就会出问题。
3. **连接要复用**（连接池 + 保活），不要每次请求都新建再销毁。
   持续高频调用下，反复建连是很多不稳定问题的来源。
4. **谁创建，谁负责关闭**。框架自己创建的客户端由框架关闭；
   使用者传进来的实例，**框架绝不能去关它**——那可能是多处共用的。
5. **出错时要能看到真实原因**。客户端抛出的异常应保留原始错误信息，
   框架向上层报告时不要把它替换成一句笼统的"调用失败"。
   同时建议异常带一个"是否值得重试"的标记，供框架决定要不要退避重试。

### 3.5 兼容性：默认什么都不变

- 不传 `client` 时，走原来的路径，行为完全一致，**现有用户不需要改任何代码**；
- 新增的都是可选参数和新模块，不修改任何已有函数签名；
- 内置的两个客户端保留不动，只是补充声明"它们实现了这个接口"。

> 一个命名上的小提醒：仓库里已经有一个文件叫 `common/clients/llm_client.py`，
> 但它的内容是 HTTP 连接池，并不是大模型客户端。如果采纳本议题，
> 建议把它改成更贴切的名字，把 `LLMClient` 这个名字让给对外接口；
> 若不便改动，本接口也可以叫 `ChatClient`，不影响方案其余部分。

## 四、分三步做

| 步骤 | 内容 | 说明 |
|---|---|---|
| **一** | 定义接口、三种用法、生命周期规则，配一套接口自测工具 | **完全不动内置实现**，纯新增，风险最低 |
| **二** | 内置客户端声明实现该接口，并顺势优化其连接管理 | 内部改造，对外无感 |
| **三** | 打通配置文件引用；补充文档与示例 | |

**怎么算做成了**，建议以这几条为准：

1. 不传客户端时，现有测试全部通过且行为不变；
2. 框架提供一个"接口自测工具"，任何实现跑一遍就知道合不合格——**内置实现自己要先过**；
3. 故意给一个不支持结构化输出的客户端配上结构化输出，**必须在搭建阶段就报错**；
4. 使用者传进来的客户端，在流程结束后**依然可用**（说明框架没有擅自关闭它）；
5. 用一个假客户端就能跑通一条带分支的流程测试，**全程不连任何真实模型**。

---

## 五、我们能提供什么

- 一份按此接口整理的客户端实现，作为参考实现或示例；
- 接口自测工具的用例；
- 在真实负载下的对照数据（内置实现 vs 自带实现的成功率与耗时）。

---

## 六、明确不做

- **不替换**内置的两个客户端，也不改它们的默认配置；
- **不引入新的依赖**，接口只用标准库；
- **不做模型选型与路由**——框架已有相关能力，与本议题无关；
- **不做图像/语音/视频**——那些应另立各自的接口，不塞进这一个。
