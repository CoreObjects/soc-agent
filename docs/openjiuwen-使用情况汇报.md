# openJiuwen 使用情况汇报 —— 现状能力与问题总结

> 面向：项目汇报 · 决策视角
> 日期：2026-07-30 ｜ 版本：openJiuwen `0.1.16`（agent-core），LLM 后端 = 昇腾 qwen（vLLM，OpenAI 兼容）
> 一句话结论：**openJiuwen 的「工作流编排」能用、单条 demo 可跑通、昇腾亲和成立；但它自带的 LLM 客户端在持续负载下实测约 50% 调用失败，且 Runner 进程单例导致无法多线程并发，不满足我们的生产轮询吞吐。当前决策是把这一层的 LLM 调用改回直连昇腾 qwen 的自研 `QwenClient`（同一个昇腾端点、实测 100% 稳），昇腾算力亲和不受影响。**

---

## 1. 背景与使用范围

- **为什么选它**：openJiuwen 是华为国产 Agent 框架（AgentOS），算力亲和昇腾——与我们研判机（server2，昇腾）匹配，故按要求选型试点。
- **我们实际用它做了什么（范围 A）**：只用它搭 SOC 研判三级漏斗里的**浅层分诊**这一档：
  `Start → LLMComponent（浅层判 needs_deep/verdict）→ BranchRouter → { 升级深度 | 终局 } → End`。
  本质是「**给一次 LLM 判定套一个工作流**」。**深度研判、经验层、处置执行都不经过 openJiuwen。**
- **更大的设想（范围 B/C，未实施）**：曾规划把整条研判流水线、skills、经验自演进都迁到 openJiuwen（含它的 `agent_evolving` 自演进/RL、`IntelliRouter` 模型级路由）。因下述客户端稳定性问题，**B/C 未推进，仅停留在设计**。

---

## 2. 现状：实际验证「能干的事」

| 能力 | 结论 | 说明 |
|---|---|---|
| 工作流编排（多组件 + 条件分叉） | ✅ 能用 | Start / LLMComponent / BranchRouter / 自定义组件 能搭能跑通 |
| 结构化输出 | ✅ 能用 | schema 约束 + tool-call，浅层稳定吐 `{needs_deep, verdict, …}` JSON |
| 昇腾算力亲和 | ✅ 成立 | LLM 跑在昇腾 qwen 上（这一点与换不换客户端无关，始终打昇腾） |
| 单条真机分诊 | ✅ 验通 | 横向登录（T1021.001）浅层正确判「需升级」，理由准确 |
| **并发 / 生产吞吐** | ❌ 不可用 | 见问题 ①②——多线程并发挂死、持续负载 ~50% 失败 |
| 自演进 / 复杂多步编排（范围 B/C） | ⬜ 未验证 | 因客户端问题未推进 |

**小结**：openJiuwen 在**单线程 / demo** 场景下，作为「工作流编排器」是能干活的；但一旦进入**并发、持续高频调用**的生产态，就被下面两个结构性问题挡住。

---

## 3. 使用过程中遇到的问题

问题分两类：**A 类是可解的工程坑**（都已找到修法），**B 类是结构性/决定性问题**（是我们改变技术路线的直接原因）。

### A. 可解的工程坑（已定位并有修法）

| # | 问题 | 现象 / 根因 | 修法 |
|---|---|---|---|
| 1 | 工作流执行超时默认仅 60s | 昇腾单次调用常 >60s，被掐断（错误码 100101）；超时值只从进程环境变量 `WORKFLOW_EXECUTE_TIMEOUT` 读，API 传参被丢弃 | 进程级设大该环境变量 |
| 2 | LLM 请求超时 + 重试放大 | 默认 `timeout=60 × (1+3 retries)` ≈ 4 分钟才失败 | `timeout=真实需要, max_retries=1` |
| 3 | qwen3 思维链未关 → 输出非 JSON | 开思维链会吐 `<think>…`，其 `json.loads` 崩（101004）；它的客户端不像自研 QwenClient 默认关思维链 | `extra_body.chat_template_kwargs.enable_thinking=False` + 低温 |
| 4 | 分支条件表达式改坏字符串 | 裸词 `true_positive` 被内部正则把 `true→True` 全局替换成非法名 | 用单引号字面量 `== 'true_positive'` |
| 5 | 会话须在运行中的事件循环内创建 | 内部依赖 `get_event_loop` | 在 `await invoke` 同协程内建会话 |

> 这 5 个坑**换掉客户端后随之全部消失**（不再引入这套复杂度）。

### B. 结构性 / 决定性问题（路线改变的直接原因）

**① Runner 是进程级单例，无法多线程并发**
- 2 并发即「跑不到出口、结果为空、挂死」；单线程完全正常。
- 根因（已读源码坐实）：`GLOBAL_RUNNER` 是进程单例，其异步态绑定单一事件循环，多 worker 线程各自的循环并发调用时相互打架。
- 影响：我们的轮询需要多并发消化积压，这条路被堵死；只能收敛到「专用单线程串行」，与生产需求相悖。

**② ★决定性坑：LLM 客户端在持续负载下约 50% 调用失败（错误码 101003）**
- 放开全量后台运行，处理约 6.5 万条告警时，**约一半在浅层 LLM 调用处失败**（`invoke llm failed`）。
- **对照实验（关键证据）**：
  - 深度侧用自研 `QwenClient` 打**同一个昇腾 qwen 端点** → **100% 成功**；
  - 浅层用 openJiuwen 的 `LLMComponent` 打**同一个端点** → **~50% 失败**。
  - 日志前半/后半失败计数几乎相等（35.07 万 ≈ 35.22 万）→ **从一开始就 ~50% 崩，不是随时间恶化的连接泄漏**。
- 判定：**同端点、同模型，唯一变量是客户端** → 问题在 openJiuwen 的 LLM 客户端本身，**不是昇腾后端、也不是网络**。

### C. 其它

- **SDK 仍在快速演进**：大量 API 已弃用（`WorkflowAgentConfig`/`AgentConfig`/`WorkflowSchema`/`DefaultResponse` 等），跟版本需持续留意。
- **环境约束**：openJiuwen 要求 Python 3.11–3.13（我们原环境为 3.10），引入它需单独建 3.11+ 环境。

---

## 4. 当前决策与理由

**决策**：浅层分诊的 LLM 调用**改用自研 `QwenClient`（直连昇腾 qwen）**，不再走 openJiuwen 的 `LLMComponent`。

**理由**：
1. **稳定性**：同一个昇腾端点，QwenClient 实测 100% 稳（对照 openJiuwen ~50% 失败）。
2. **并发**：纯 Python、无单例/事件循环耦合，可多线程并发消化积压。
3. **简化**：换掉后，上面 A 类 5 个坑连同并发困难一起消失，浅层代码反而更简单。
4. **昇腾亲和不变**：仍然打昇腾 qwen，算力亲和这一初衷完全保留。

> 换句话说：**「用 openJiuwen 编排」这件事对「只包一次 LLM 调用」的场景，收益（编排）远小于它带来的成本（客户端不稳 + 无法并发 + 版本动荡）。**

---

## 5. 对 openJiuwen 的定位判断

- **它的强项**：工作流编排（多组件、条件分叉、结构化输出）本身是可用的，对**真正复杂的多步 agent 流程**可能仍有价值。
- **它的短板（对我们这类生产场景）**：自带 LLM 客户端在持续负载下不稳（~50% 失败）、Runner 单例不能并发、SDK 版本动荡。
- **结论**：**对「一次 LLM 判定」这种轻场景，性价比不划算**；是否用于更复杂流程，取决于其客户端与并发问题是否解决。

---

## 6. 后续建议

1. **保留昇腾亲和、用稳的客户端**：现状（QwenClient 直连昇腾）已同时满足「昇腾算力 + 生产稳定」，建议作为当前基线。
2. **若要继续用 openJiuwen**：可将其**降级为纯编排骨架**、把 LLM 调用注入 `QwenClient`（绕开其 `LLMComponent`）；但 Runner 单例并发问题仍需以「专用单线程串行」规避，代价较高。
3. **向华为 openJiuwen 团队反馈两个产品级问题**（有实测证据，值得他们改进）：
   - `LLMComponent` 客户端在持续负载下 ~50% 失败（101003）；
   - `Runner` 进程单例、无法多线程并发。
   若这两点被修复，openJiuwen 作为昇腾原生编排框架的价值会明显提升，届时可重新评估范围 B/C。
