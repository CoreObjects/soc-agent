# 告警研判分档路由方案：规则档快速通道 + 大模型慢速通道

## 一、总体架构：三级漏斗

告警研判按"这条告警需要多深的处理"分成三级，逐级放行、逐级升级。真正的路由主轴不是告警所属的层（application/host/identity/network），而是**这条告警需要的取证与研判深度**；层是相关变量，不是主变量——因为同在应用层的 `webshell` 需要跨层坐实、必须上大模型，而名义在主机层的 `registry_persistence` 大多是安装器写自启、决策树很浅。

三级的定位如下：

| 档位 | 载体 | 是否用 LLM | 核心 KPI |
|---|---|---|---|
| **规则档（快速通道）** | 行为指纹 + 威胁判定规则 | 否，纯确定性执行 | 在保持 recall 的前提下，把送进慢速通道的量压到最低 |
| **快速档 9B（慢速通道·一级）** | 精简 SKILL_fast + recipe_fast | 是，小模型 | 在保持 recall 的前提下，把送给 122B 的量压下来 |
| **深度档 122B（慢速通道·二级）** | 完整 SKILL + recipe_full | 是，大模型 | 高保真定性，跨层融合、父子链还原、序列/盲区推理 |

关键在于理解三者的漏斗关系：**规则档是第零级，用沉淀下来的经验做零成本的确定性复用；只有规则档解不了的，才流进 LLM 慢速通道；慢速通道内部再按取证深度分 9B / 122B 两级。** 而慢速通道每判一条新案例，就把结论蒸馏回规则档，让第零级越用越宽。每一级的使命都是同一句话——在不丢真攻击的前提下，把交给下一级的量降下来。

```
告警
 └─ 分类 → recipe_fast 取证 → 发现列表(findings)
      │
      ├─【规则档 / 快速通道 · 无 LLM】
      │     命中误报业务指纹 ──────────────→ 判 FP，复用处置剧本，终局
      │     命中威胁指纹 → 过威胁规则 → 命中 → 判 TP，附依据，进人工优先队列
      │     (升级门 tripwire 命中则跳过本档捷径，强制升级)
      │     都未命中 / 规则未中 ────────────┐
      │                                     ↓
      └─【慢速通道 · LLM】
            快速档 9B ── 决策浅、FP 占大头的类别，小模型降噪
            深度档 122B ─ 跨层取证、父子链、Kerberos 序列、SAN/EKU 盲区
                 ↓
            产出 verdict → 蒸馏新指纹 / 新规则 / 新剧本 → 回流规则档
```

## 二、规则档：即我们的快速通道

规则档不是"某几个 skill 的分类桶"，而是一道**横跨所有告警类别、跑在任何 LLM 之前的第零级**。任何一条告警，分类、跑完 `recipe_fast` 得到发现列表之后，先无条件走一遍规则档；命中即终局或直接定性，未命中才升级到慢速通道。它承担整个系统的降噪主力。

### 2.1 输入：规范化发现列表

规则档消费的不是原始取证文本，而是 `recipe_fast.py` 产出的 `findings`。每条发现是一个语义观察加原始证据，并归一到该告警类的发现词典（规范发现编号），实例值抽象为类型占位符（`<EXTERNAL_IP>`、`<USER>`、`<HOST>`），连续值离散分桶，时间戳/PID/随机端口等易变字段禁入。这样两次本质相同的取证会产出尽量相同的发现集合——对无关差异钝感，对决定性差异敏感。取证结果格式千奇百怪的问题，在发现列表这一层就被消解掉了。

### 2.2 三步匹配

**第一步，匹配误报业务指纹。** 误报业务指纹是从历史误报案例蒸馏出的"良性解释"白发现集合——触发源是内部漏扫资产、进程有合法厂商签名且由运维软件拉起、所谓恶意域名实为白名单业务域名、操作对得上变更工单、命令是每天例行的备份脚本等。原先 recipe 层用 `provisioning_noise()` 打标签直接判 FP 的那类（Ansible 供给噪声、`__PSScriptPolicyTest_` 自检），在新架构里只是"内置的一条误报指纹"，是这一步的特例。命中误报业务指纹（决定性白发现命中 + 加权重合度达标）即判 FP，复用经验中已沉淀的处置剧本（归档/降级），流程终局。这是吃掉每天成百上千条重复假告警的主出口。

**第二步，匹配威胁指纹并过威胁规则。** 威胁指纹只承担召回作用——"这个案子长得像历史上那起"——命中后不直接定性，而是转入威胁判定规则核验。威胁判定规则用受限的解释性语言（DSL）描述真威胁的定性条件（规范发现存在性、数值/桶比较、与或非、同源关联谓词），由解释器对发现列表确定性执行，规则存 openGauss（JSONB 表达式树）并 Redis 热加载。规则命中即采信为 TP，附上命中的规则作为定性依据，进入人工优先队列并复用经验中的处置剧本。

**第三步，两类指纹都未命中，或威胁指纹命中但规则未中。** 这类无法用既有经验复用，升级到慢速通道。为降低漏判风险，威胁指纹未命中时也把本类全部威胁规则执行一遍再决定升级——发现集合通常只有几条到几十条，全量执行规则是毫秒级成本。

### 2.3 匹配方式

匹配在同告警类分区内进行，跨类不发生。技术上两层：规范发现编号的倒排索引做召回（毫秒级），再对候选算加权重合度排序。发现在蒸馏时标注权重等级——决定性发现、佐证发现、环境噪声——打分以决定性发现优先，绝不用集合全等，因此佐证缺一条、多采到一条噪声，都不影响命中。红白两类指纹权重逻辑不同：威胁匹配看红发现的加权重合够不够，误报匹配还要多看红发现是否被历史案例完全解释。

### 2.4 KPI 与运营护栏

规则档的 KPI 是**在保持 recall 前提下把升级量压到最低**。被误报指纹压掉的告警不删除，保留抽样回看；若压掉的告警后续出现新增的、未被历史案例解释的红发现，仅做记录告警而不阻塞主流程——宁可配一个便宜的事后纠错回路，不配昂贵的事前审批。

## 三、升级门（tripwire）：守住规则档的降噪捷径

规则档"命中误报指纹即终局"是效率来源，但如果没有护栏，会降噪过头漏掉真攻击。因此在规则档的 FP 捷径上设几条一票否决的升级门：**只要命中，无论误报指纹是否也命中，都跳过规则档的终局判定，强制升级到慢速通道（多数直接进深度档）。**

- **关键资产兜底**：资产是 `domain_controller` / `certificate_authority` 等 critical 级别 → 直接跳深度档 122B，不走规则档捷径，也不走 9B。
- **`web_exploit` 得手临界**：WAF 命中 `outcome == passed` 且跨层 pivot 到后端主机发现任何落地（w3wp 派生进程 / 写脚本 / 外连）→ 立即升级。这是"尝试→得手"的临界，判"尝试"规则档/9B 够用，判"得手"必须上大模型。
- **`ingress_tool_transfer` 落地即用**：`落地即执行 == true`，或同主机同时间窗内存在其他攻击链告警 → 升级。
- **`suspicious_outbound` LOLBin 发起**：发起进程是 rundll32 / mshta / regsvr32 / 无签名 powershell 等 LOLBin → 升级。
- **未解释红发现**：新案例命中了某条误报指纹，但同时存在该误报经验未覆盖的红发现 → 升级，不许复用误报结论。

升级门以声明式条件写进每个 skill 的前置元数据（见 4.4 的 `escalate_to_deep_when`），不写进路由器代码，加新 skill 时不用改路由逻辑。

## 四、慢速通道：快速档 9B + 深度档 122B

规则档解不了的告警进入 LLM 慢速通道，按取证深度再分两级。

### 4.1 快速档 9B —— 漏斗的第一级 LLM，不是"小模型将就用"

9B 的定位是漏斗第一级，KPI 是在保持 recall 的前提下把送给 122B 的量降下来，而不是"能力弱的备胎"。它处理决策浅、FP 占大头、SKILL.md 本身就写着"核心是降噪"的类别。

重点：**别把同一份 SKILL.md 喂给两个模型。** 9B 会被完整方法学文档里那些"留给 122B 的深挖分支"淹没，反而判得更差。为快速档单独写 `SKILL_fast.md`，只保留"证伪五步"和"良性场景清单"，删掉深度决策树。路由器按分档拿哪一份。

### 4.2 深度档 122B

122B 处理需要跨层融合、父子链取证还原、Kerberos 序列、call_trace 语义、SAN/EKU 盲区推理的类别，喂完整的 `SKILL.md` 与 `recipe_full.py` 的全量证据。深度档的产出是高保真定性——TP 结论仍交人复核，但研判依据、缺失证据、绑定实体都由大模型补齐。

### 4.3 Recipe 也要分档

模型再小，取证还是重的，所以 recipe 必须同步分档。`recipe_fast.py` 只跑关键几个查询（如 `web_exploit` 只取 WAF 请求 + 源 IP 画像），供规则档与快速档使用；`recipe_full.py` 追加跨层 pivot，供深度档使用。升级时把 fast 档已取的证据传给下一级，避免重复取证。规则档消费的发现列表就来自 `recipe_fast`。

### 4.4 分档写进 skill 前置元数据

分档、升级门、技术编号都写进 skill 的 front matter，不写进路由器逻辑，保证加新 skill 时路由代码零改动、一致性可维护：

```yaml
---
name: web_exploit
layer: application
tier: fast              # rule | fast | deep
escalate_to_deep_when:
  - "recipe.请求与WAF命中.outcome == 'passed'
      AND recipe.跨层-后端落地 has any of {web_spawned, web_wrote, web_outbound}"
  - "recipe.源IP的WAF打击画像.distinct_crs_rules >= 8"
technique_ids: [T1190, T1059.007]
---
```

### 4.5 慢速通道分档建议

规则档是横切第零级，对所有类别生效；下表是**规则档未命中、升级进慢速通道后**，各类别默认走 9B 还是 122B：

| 慢速通道档位 | Skill | 理由 |
|---|---|---|
| **快速档 9B** | `web_exploit`、`_generic/application`、`ingress_tool_transfer`、`suspicious_outbound`、`registry_persistence`、`_generic/host` | 决策浅、FP 占大头，SKILL.md 自述"核心是降噪" |
| **深度档 122B** | `webshell`、`suspicious_process`、`lsass_dump`、`c2_beacon`、`kerberoast`、`dcsync`、`lateral_movement`、`adcs`、`_generic/identity`、`_generic/network` | 涉及父子链取证、跨层融合、Kerberos 序列、call_trace 语义、SAN/EKU 盲区推理 |

注意 `webshell` 虽是应用层却进 122B——它自己的 SKILL.md 明写"应用层证据最薄、最必须靠跨层坐实，真正高保真信号在主机侧"，丢给 9B 就废了。这再次印证路由主轴是取证深度而非层。

## 五、回流：慢速通道反哺规则档

慢速通道每走一条案例，都要把结论蒸馏回规则档，这是三级漏斗能自我增厚的关键，缺了它规则档就只是一个静态库。

判为误报的案例，蒸馏出导致假告警的业务行为白发现集合，形成新的误报业务指纹；判为威胁的案例，蒸馏出定性依据的红发现集合（威胁指纹）与威胁判定规则（DSL）。蒸馏本身几乎零成本：慢速通道的研判环节本来就在读发现列表、出结论，让模型在同一次调用里额外输出"我依据的是哪几条决定性发现 / 定性条件"，指纹与规则就自然产生了。

新蒸馏的威胁规则必须过"考试"才激活：回放原案例（对着蒸馏它的那个案例执行必须命中）+ 历史误报回归（对同类历史已确认误报批量执行，命中任何一条即打回）。两关都过才进 openGauss / Redis 生效。走兜底取证的告警样本、被推翻的规则、映射失败的自由文本发现，统一进离线迭代队列，定期由更强模型或人工消化成新的类别脚本、发现词典条目或规则。

于是漏斗形成正循环：慢速通道判过的模式，下次同类告警在规则档零成本命中；规则档命中越多，慢速通道越省；只有真正新颖的告警才消耗大模型。

## 六、统一 verdict schema：三档同构

三档必须产出同构的判定结果，下游（响应组装、反馈闭环、复盘评测）不应关心是哪一档、哪个模型判的：

```
{
  verdict,          # TP | FP | escalate
  confidence,
  missing_evidence, # 触发升级的缺失证据
  bindings,         # 绑定实体
  evidence_refs     # 规则档填命中的指纹/规则ID；LLM档填引用的发现
}
```

这条不落实，以后想做"9B 判错率对齐 122B""规则档 FP 复用是否可靠"这类评测会非常难。规则档的 verdict 里 `evidence_refs` 记录命中的指纹编号与规则 ID，天然可解释——命中了哪条经验的哪段依据一目了然。

## 七、落地要点小结

- **规则档是横切第零级**，对所有类别生效，跑在任何 LLM 之前；`tier: fast/deep` 是"规则档未命中后"的慢速通道路由，两者不冲突。
- **取证先行、且分档**：`recipe_fast` 产出发现列表供规则档与 9B，`recipe_full` 供 122B，升级时传递已取证据避免重复。
- **升级门守住降噪捷径**：关键资产、得手临界、LOLBin、未解释红发现一票否决，强制跳过规则档终局。
- **分档与升级门写进 front matter**，不写进路由器；快速档单独出 `SKILL_fast.md` 精简版。
- **回流蒸馏 + 规则考试**：慢速通道结论反哺规则档，新规则须过回放与历史回归双关。
- **对底层数据库（openGauss）的诉求**：离散发现集合的倒排召回与加权重合度检索（指纹匹配）、JSONB 存规则表达式树与经验元数据、常规结构化存储支撑台账与生命周期；Redis 承担热规则与热指纹缓存。业务侧负责发现词典、变量抽象、DSL 与解释器、考试流水线、蒸馏与回流编排。
